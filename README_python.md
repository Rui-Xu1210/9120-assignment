# Pediatric Vaccination Tracker API

Python REST API for the PostgreSQL schema in `sql_code_por.sql`. It gives a future frontend a stable HTTP interface for parent and child setup, vaccine lookup, schedules, vaccination history, reminders, and dashboard counts.

## 1. Prepare the database

Create a PostgreSQL database, then run `sql_code_por.sql` followed by `Insert_dataset.sql` in that database. The app expects the default `public` schema and the lowercase table/column names created by PostgreSQL from those unquoted SQL identifiers. Do not use the earlier draft `sql_code.sql`.

The database must be reachable from this computer. Copy `.env.example` to `.env` and set the connection values to match the database you created. Keep `.env` private; it is excluded from version control.

## 2. Install and start

```bash
python3 -m venv .venv
source .venv/bin/activate       # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

The API runs at `http://127.0.0.1:8000`. Interactive API documentation is at `http://127.0.0.1:8000/docs`; OpenAPI JSON is at `/openapi.json`.

For step-by-step setup on another teammate's computer and instructions for connecting a phone over local Wi-Fi, see [FRONTEND_HANDOFF.zh-CN.md](FRONTEND_HANDOFF.zh-CN.md) or [FRONTEND_HANDOFF.md](FRONTEND_HANDOFF.md) (English).

## API overview

| Method | Route | Purpose |
|---|---|---|
| GET | `/health` | Check API and database connection |
| GET, POST | `/parents` | List or create parents |
| GET | `/parents/{parent_id}` | Parent and their children |
| GET, POST | `/children` | List or create children; database trigger creates schedules/reminders |
| GET | `/children/{child_id}` | Child profile, vaccination history, and schedule |
| GET, POST | `/vaccines` | Search vaccine catalog by name/type or prevented disease; add a vaccine |
| GET | `/schedules/recommended` | List recommended vaccine doses |
| GET | `/schedules` | Browse schedules; filters: `child_id`, `status`, `overdue=true` |
| PATCH | `/schedules/{schedule_id}` | Set appointment date/provider/status |
| GET, POST | `/records` | Query history or record an administered dose |
| GET, PATCH | `/reminders` and `/reminders/{reminder_id}` | Query reminders or update reminder status |
| GET | `/dashboard` | Summary counts for the frontend |

### Example requests

Create a parent:

```json
POST /parents
{"name":"Alex Lee"}
```

Create a child (use the returned parent ID):

```json
POST /children
{"name":"Sam Lee","date_of_birth":"2025-01-15","parent_id":"P00001"}
```

Set an appointment date and provider:

```json
PATCH /schedules/S00001
{"scheduled_date":"2025-03-15","provider":"City Medical Centre","status":"pending"}
```

Record a completed vaccination:

```json
POST /records
{"child_id":"C00001","vaccine_id":"V00001","dose_number":1,"vaccination_date":"2025-01-15T10:30:00","provider":"City Medical Centre"}
```

`vaccine_id` is generated by the database. Look it up through `GET /vaccines` rather than assuming IDs follow vaccine insertion order.

## Data and business logic

- Adding a child runs the existing PostgreSQL trigger, which creates one schedule and reminder for each recommended dose. The returned `schedules_created` value helps the frontend confirm that setup.
- Adding a vaccination record runs the database trigger to mark its matching schedule and reminder completed. The record insert and trigger updates share one transaction.
- `GET /schedules?overdue=true` defines overdue as pending with a scheduled date before the database's current date.
- Schedule dates can be changed by a parent through the schedule update route. The initial dates are calculated from birth date plus each recommended age by the SQL trigger.
- Request bodies are validated and all values are passed as SQL parameters. IDs and credentials are not generated or embedded in Python.

## Notes for the frontend team

- All responses are JSON. Use `/docs` to inspect request fields and response shapes while implementing the UI.
- Errors use standard HTTP status codes: `404` for missing referenced rows, `409` for duplicate dose records, `422` for invalid input, and `503` when PostgreSQL is unavailable.
- The current schema has no authentication or authorization. Add that before exposing the service beyond a local/demo environment.
